RX1/RX2 parity & two-slices-per-RX proposal

Recommendations only — no project changes made. Based on the current app code (MainViewModel.Slices.cs, MainViewModel.Noise.cs, MainViewModel.Agc.cs) and the engine fork (external/station-engine, contract Dtos.cs).

1. How it works today

The app has one bank of receive controls (mode, filter, AGC, NB/NR/ANF, squelch, RX leveler, mode options, RX EQ) that always acts on the active receiver. The RX1/RX2 badges beside the frequency move that focus. When the second receiver is on, several of its settings are mirrored — forced to a copy of the active receiver's values rather than kept independently:

  • Filter — MirrorFilterAsync copies every filter change to the other slice (sideband-flipped). You cannot run a 2.7 kHz USB filter on RX1 and a 500 Hz CW filter on RX2; the last change wins on both.
  • NB/NR/ANF/SNB + all their parameters — SendNrAsync pushes the whole NrConfig to both receivers.
  • AGC — auto/manual, speed, fixed gain and AGC-T are each sent to both receivers (ToggleAgcAutoAsync, SelectAgcSpeedAsync, OnAgcTopDbChanged, OnAgcFixedGainDbChanged).

Mode and filter can differ between slices (slice B starts as a copy, then keeps its own), but only because switching the active receiver reloads them — there is no UI showing or editing the inactive receiver's settings without taking focus away from the other one.

2. Gap analysis — what the engine actually supports

The key finding: the engine already supports independent per-receiver mode, filter, filter presets, AGC and the entire noise block (ReceiverSetRequest takes Mode, FilterLowHz/HighHz, FilterPresetName, NrMode, Nr, Agc, AgcTopDb, AutoAgcEnabled per index; ReceiverDto returns them per index). RX2 parity for those is an app-side change only — no engine patch needed. A handful of features are engine-global and cannot be per-RX without engine work:

3. Recommendation 1 — RX parity with minimal CPU/performance impact

Keep the "active receiver" control model — don't duplicate the control bank

The current focus-follows design is the right one for CPU and screen real estate: there is still exactly one DSP chain per enabled receiver (that cost lives in the engine and doesn't change), and the app adds no widgets, no extra bindings and no extra timers. All that changes is whose values the single control bank holds at any moment. Two layout alternatives are mocked up in section 4, but the data model below is the same for both.

What changes (conceptually)

  1. Stop mirroring. Remove the slice-B copies in SendNrAsync, the AGC send paths and MirrorFilterAsync. Sends become index-aware: use the existing per-receiver route (SetReceiverAsync(1, …)) for RX2 and the flat endpoints (or index 0) for RX1.
  2. Cache per-receiver state. Keep a small record per receiver — mode, filter cuts + preset, NrConfig, AGC mode/top/fixed/auto — refreshed from ReceiverDto on the existing 1 s poll (it already carries all of these fields). MakeActiveAsync already reloads frequency/mode/filter on a switch; extend it to restore that receiver's AGC and noise settings into the controls, exactly the way it does today for the active slice.
  3. Surface the inactive receiver's state where the eyes already are. The MiniVFO chips on each panadapter already show frequency, mode and TX state. Add the filter preset name and lit-state dots for NB/NR/AGC (small, passive readouts — no new controls). The operator then sees "RX2: 7.055 CWU 500 · NR2" at a glance and only takes focus to change it.
  4. Label the genuinely shared items. Squelch, RX Lev, RX EQ and the AM/FM option panels get "(both RX)" in their tooltips. Attempting per-RX there would need engine changes for very little gain — and being explicit beats silent coupling.
CPU/performance impact: effectively zero. No new receivers are created, no new streams, no new polls. The only behavioural difference is that filter/NR/AGC parameters may now differ between two receivers — but both receivers already run those DSP blocks; only their coefficients change. Memory cost is a few cached structs per receiver. The 1 s poll and Latest<T> throttled senders are unchanged.

5. Recommendation 2 — two slices on each RX (up to 4 slices)

The engine can already do it

The engine is built for a uniform receiver-index model and supports up to 10 receivers (WireContract.MaxReceivers). Practical ceilings depend on the radio: Protocol-2 boards offer 8 user receivers on Hermes-class/Saturn and 6 on other Orion-family boards (the first DDCs are reserved for the PureSignal feedback pair); plain Protocol-1 is capped at 2. Extra receivers must be contiguous — enabling receiver n implicitly enables everything below it. Each receiver already carries its own VFO, mode, filter, presets, AGC, noise block, AF, mute, zoom and ADC source.

What changes in the app

  • Data model: the current "receiver 1 is either slice B on RX1's panadapter or RX2, never both" rule (MainViewModel.Slices.cs) becomes a slice list — e.g. slices 0–1 on panadapter A, slices 2–3 on panadapter B, each panadapter rendering two passbands and two flags (the rendering already exists for the A/B-on-one-panadapter case).
  • Controls: the focus-follows model from Recommendation 1 extends naturally: the RX1/RX2 badges choose the panadapter, and a second badge pair (A/B per panadapter, exactly like today's AbBadges) chooses the slice within it. No new control categories.
  • TX: the single TX receiver is engine-global; transmitting slice becomes any of the four.
The real cost is DSP, not UI. Every slice is a full WDSP chain plus a DDC stream — on a Raspberry Pi 5 two slices is comfortable, four is the ceiling worth supporting, and only P2 radios can even reach four. Mitigations: (1) default new slices to off; (2) show per-engine CPU near the slice add control (the CPU readout already exists in the status row); (3) cap slices at EffectiveMaxReceivers from engine state and say why; (4) reuse the existing "one panadapter pair" rendering — two slices per pan draw as two passbands, not two more spectrum views, so display CPU is unchanged.
